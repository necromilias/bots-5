# Security

## Scope and trust model

This repository contains both the closed V0/V0.2 campaign harness and the native Linux desktop product.
Their capability surfaces differ, but the same high-level rule applies: **model output is untrusted data
and does not acquire authority merely by being generated by a model.**

The operator and explicitly supplied configuration are trusted. B.O.T.S. is not a hardened hostile-local-
operator sandbox and does not claim protection against arbitrary malicious same-UID injected code,
ptrace/descriptor theft, privileged namespace/mount manipulation, kernel compromise, or lying storage.

## Campaign harness

The V0/V0.2 campaign harness reads only its job file and explicitly declared input/prompt files and writes
beneath the validated resolved run directory. Workers have no shell, filesystem tool, Git tool, RAG,
repository mutation, recursive delegation, or plugin capability. They return text only.

Every model receives a harness-owned execution boundary above its validated worker contract. INPUT and
WORKER OUTPUT blocks remain untrusted data even when they contain instructions, role claims, or commands.
Prompt construction is deterministic; model obedience remains probabilistic.

The campaign cost threshold is a synthesis gate over known worker subtotal, not a hard whole-run spend
limit. Unknown provider cost remains unknown.

## Linux desktop authority boundary

Linux v0.1 is landed through Phase 6. It has consequential local persistence and therefore a stronger,
explicit ownership boundary than the old campaign harness.

One `DataRootAuthority` owns an authoritative data root. Forward application/store/database/event/filesystem
effects require phase-appropriate authority ownership. Invalidation closes new admission immediately and
revokes the discovering grant. Already-owned cleanup may release resources but cannot silently reacquire
forward authority.

SQLite is authoritative mutable application state. Attachment payloads are filesystem-backed and
content-addressed. The rooted SQLite/native VFS and attachment layer preserve descriptor-rooted ownership,
durability barriers, resource lifetime, and outcome classification. Authoritative corruption or uncertain
consequential state fails closed rather than being converted into ordinary success.

The finite participation inventory and closure evidence are:

- `UNIFIED_AUTHORITY_EFFECT_INVENTORY.md`;
- `LINUX_V0_1_PHASE6_IMPLEMENTATION_REPORT.md`;
- `LINUX_V0_1_PHASE6_CLOSURE_REPORT.md`.

Future Android/remote clients must talk to the authority; they must not independently open the live
authoritative database.

## Secrets

### Campaign harness

`OPENROUTER_API_KEY` and optional schema-v2 local-provider credentials are read from named environment
variables at runtime. Resolved secret values must not be written into manifests, resolved jobs,
run/stage metadata, usage, events, status/inspect output, examples, or generated project files.

### Linux desktop

The accepted desktop design uses a core-owned SecretStore abstraction. Interactive Linux credentials use
Linux Secret Service through Python keyring/secretstorage; environment-variable credentials remain an
explicit headless/deployment source. Never silently fall back to plaintext credential storage.

Database/client/log/export state may contain non-secret configuration, references, and credential status,
but not resolved credential values.

## Network/provider boundary

The V0.2 local provider accepts only an operator-supplied HTTP/HTTPS API base, rejects URL userinfo/query/
fragment/surrounding whitespace, appends `/chat/completions`, and performs no endpoint/model discovery.
Without configured authentication, no authorization header is sent.

The Linux desktop provider/backend contract must preserve truthful dispatch, completion, cancellation,
usage/cost, and remote-outcome certainty. Generation requests are never invisibly retried once external
acceptance or spend is uncertain.

Ordinary automated tests must not make provider calls or spend money. Live/provider acceptance is
explicit and opt-in.

## Filesystem and persistence

Legacy campaign run-directory protections reduce accidental traversal/symlink mistakes but are not a
hostile filesystem sandbox.

For Linux desktop authoritative state, mutable pathnames are not sufficient authority after data-root
acquisition. Rooted descriptors/claims, fresh validation, durability fences, and common invalidation
classification govern consequential filesystem/database work. Live authoritative SQLite state is local to
the authority host and must not be shared by placing the database on Samba/NFS for multi-host access.

Backups/import/export/recovery remain later Linux v0.1 phases; their future implementation must preserve
the single-authority and verified-adoption rules in `LINUX_V0_1_DESIGN.md`.

## Consequential actions beyond current Linux v0.1

Future shell/tools, Code/Git mutation, MCP/plugin frameworks, remote execution, Android control, schedulers,
and other consequential capabilities require explicit B.O.T.S.-owned authority, provenance, bounded
permissions, and human-adjudicated policy before use. Model output alone is never sufficient authority.
